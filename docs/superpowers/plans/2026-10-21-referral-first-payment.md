# RefRef: минимальный план реферальной первой оплаты

**Статус:** согласованный контракт реализации. «Только план» относилось к подготовке 2026-10-21; выполненная работа, проверки и незакрытые gates записаны в [общем отчёте](../../../../ai-backend-marketing-agent/docs/superpowers/reports/2026-10-21-referral-first-payment.md).
**Goal:** Double-Sided как полноценный общий шаблон, проверка кода, первая оплата существующего владельца биллинга backend, комиссия и ручная выплата в RefRef.
**Architecture:** текущие Fastify/Next/tRPC/Better Auth/PostgreSQL/Drizzle; native participant → referral → event → reward. Backend владеет тарифами/ценой/ВТБ/подпиской. **Без outbox, новых workers, очередей и гарантированной фоновой доставки.**
**Spec:** последние уточнения пользователя: использовать существующие модели обоих проектов; RUB добавить к поддерживаемым валютам, не заменить USD; разработка возвратов исключена из текущего объёма. Outbox и гарантированная фоновая доставка также исключены. [Backend: C2, матрица A](../../../../ai-backend-marketing-agent/docs/superpowers/plans/2026-10-21-referral-first-payment.md); [mobile](../../../../ai-marketing-agent-user-mobile/docs/superpowers/plans/2026-10-21-referral-first-payment.md).

**Уточнение 2026-10-24:** firstPaidOnly — условие отдельной программы, не глобальный запрет повторных комиссий RefRef. Конкретные шаблоны инкапсулируют descriptor/schema/form capabilities/mapping/rule factory за существующим статическим реестром. Referrer может иметь только аккаунт RefRef, без аккаунта/подписки AI-маркетолога; buyer/customer остаётся в backend. Прежние approvals, история и обычные программы сохраняются.

**C1 — независимые стороны:** ReferralCodeResolution содержит явную `currency: CurrencyType` независимо от cash rules. Выключенная комиссия — `commission:{basis:null,rules:[]}`; непустые rules требуют явной enum basis. ACK с пустыми rewards/rewardIds полон только для пустого ожидаемого набора, не для потерянных ожидаемых начислений. Snapshot сохраняет прежний `pricing.currency`; новых денежных столбцов/нулевых reward rows нет. Перед финансовым approval обязательна валюта включённой стороны.

## Обязательные правила реализации

- Максимально готовые и нативные решения текущего стека: существующие Fastify/tRPC/Better Auth, Drizzle/PostgreSQL, общие Zod schemas, SDK и компоненты. Перед своей реализацией дважды проверить исходники и официальные рекомендации; новые пакеты/обёртки требуют конкретной недостающей функции. Модульность — общий существующий расчёт и небольшие модули шаблонов, не новая архитектура/универсальный framework.
- Многопользовательская/мультитенантная изоляция обязательна на read/write/aggregate: проверенный organization → разрешённый product → участник/операция; свой кабинет выводится из проверенной личности, не из participantId/email клиента. Новый финансовый путь не выбирает «первый продукт организации». Служебный API key сейчас ограничен организацией, не отдельным продуктом: dedicated integration scope и явная проверка разрешённого product/program обязательны, без новой системы ролей.
- Наш backend tenant и organization/product RefRef — разные уровни владения; не смешивать их и не подставлять фиксированные IDs. Реальные связи подтверждаются сервером, проверки используют несколько независимых scopes и идентификаторы, созданные для теста.
- Общих БД, межсервисных SQL/FK, общих ORM моделей, монтирования данных или копии банковских секретов нет. RefRef владеет своими participant/referral/event/reward/payout; наш сервер — оплатами/подписками. Связь — только по защищённым HTTP контрактам и внешним идентификаторам.
- **Предметная граница RefRef:** реферальная система и в дальнейшем направление лояльности, не подсистема интеграций агента. Backend работает через отдельный предметный модуль referrals; ни каталога интеграций/agent tools, ни ConnectorTokenService/permissions для RefRef не добавлять. Аналогия с Open Connector касается только отдельного сервиса, API-клиента и доступов. Подходящий готовый SDK/контрактные типы разрешены; свои данные/ORM/миграции, native механизмы и независимые сборки/развёртывания сохраняются. Будущую лояльность сейчас не реализовывать и не готовить для неё универсальный framework.
- **Код по предметной ответственности:** шаблон описывает настройки программы; общие механизмы связывают участника с пригласившим, записывают покупку и рассчитывают начисления; выплаты имеют собственные операции и проверки прав. HTTP/tRPC обработчики используют эти механизмы, а не дублируют расчёты или SQL для каждого шаблона. Не смешивать шаблоны, начисления, выплаты и банковские платежи нашего продукта в одном сервисе; следовать существующей структуре, без новой архитектуры/класса на каждую операцию.
- **БД по сущностям:** participant, код, referral, event, reward и payout не заменяют друг друга; у каждой самостоятельной сущности сохраняются свои связи, жизненный цикл и права. Не складывать отдельные операции/историю выплат в JSON события или программы. JSONB допустим для настроек/неизменяемого снимка в описанных границах, не вместо финансовых сущностей и FK/unique. Число таблиц определяется моделью: R3 допускает одну payout запись для одной заявки с одним полным исполнением; самостоятельные перечисления или распределения по начислениям требуют соответствующих связанных сущностей, а не массива внутри заявки. Не дробить тесно связанные атрибуты одной сущности ради количества таблиц.
- Из [C0 плана сервера](../../../../ai-backend-marketing-agent/docs/superpowers/plans/2026-10-21-referral-first-payment.md) обязательны OpenAPI/проверки форматов и ответов, единые деньги/время/ошибки, явная авторизация и защита от повторов. Fastify использует свои штатные route schemas, tRPC — существующие процедуры; не переносить Hono или общую обёртку на все сервисы.
- **До собственной реализации:** прочитать AGENTS/инструкции, официальные docs установленной версии и реальные exports/types/callers; затем подходящие статьи сопровождающих, руководства/cookbooks. Зафиксировать URL/версию/вывод/отличия; повторно проверить отсутствие готового решения. Native типы/интерфейсы/SDK и стиль проекта первичны, не классы/обёртки ради формы. Общий регламент — C0.1 backend.
- **Обновления разрешены:** поддерживаемую библиотеку можно обновить/добавить ради конкретной native возможности, удаления самописной части или security fix. До изменения проверить поддержку/лицензию/зависимости, migration guide/совместимость/ресурсы; совместно обновить consumers/lockfile/контракты и проверки. Не latest ради latest и не новая архитектура под библиотеку. Здесь текущие зависимости пока не меняются.
- **Хардкод и запас:** изменяемые ставки/условия — в program config, runtime identities — из verified context, адреса/секреты/лимиты — из действующей конфигурации/policies. Никаких fixed user/tenant/workspace/account IDs. Schema versions/enum/API paths/единицы — допустимые именованные константы. Расширяемость — существующие модули шаблонов/DTO/completePayout, без пустого универсального plugin framework; границы одной payout таблицы не скрывать.
- **Skills:** обязательны релевантные Superpowers и ponytail: using-superpowers/writing-plans для планирования, executing-plans либо subagent-driven-development при реализации, test-driven-development/systematic-debugging по задаче, verification-before-completion и review до готовности. ponytail-review не заменяет correctness/security проверку. Не применять все навыки подряд ради количества.
- **Новые skills разрешены по необходимости:** проверить источник/версию, прочитать SKILL.md/scripts/hooks/зависимости/права до запуска. Никаких непроверенных installers, выгрузки кода/секретов или скрытой смены инфраструктуры. Есть подходящий установленный навык — использовать его, не устанавливать дубликат.

**Уточнение о владельце кода:** в текущем API/UI операции перепривязки refcode не найдено (`root.ts:1–39`, routes app.ts:62–74); добавлять её не планируется. В БД столбцы mutable, а удалённый текст кода теоретически можно занять заново, но это не работающий пользовательский сценарий. Нужны сохранённые codeId/условия и защита финансовой истории от изменения правил/каскадного удаления, а не выдуманная функция смены владельца.

## Что удалено из проекта решения

- Outbox/dispatcher/retry/backoff/DLQ/redrive и новые фоновые процессы — **ничем не заменяются**. Не прятать очередь в metadata, таблицу pending tasks или существующий webhook worker.
- Хранимые quote/prepare в двух сервисах, preview TTL, отдельные quote/conversion/ledger/attempts таблицы — не нужны. Условия сохраняет backend один раз в существующей записи оплаты; подтверждение использует native event/reward.
- Общая миграция всех денег RefRef в minor units, новая система permissions, вторая самописная копия SDK/общий платёжный бизнес-пакет и универсальный template framework — не нужны. Это не запрет готовых API-клиентов/SDK и обоснованных обновлений по правилам выше.
- Ошибка проверки промокода — отказ применить код, **не запрет обычной оплаты**. В поле может остаться неверный код; тарифы базовые, mobile не передаёт referral, backend не вызывает RefRef для этой покупки. Применённое предложение и черновик поля — разные состояния, без новой инфраструктуры.

**Возвраты вне текущего объёма:** не добавлять refund API/events, нормализацию частичных сумм, автоматическую коррекцию комиссии, reversal/debt поля и соответствующие миграции. Уже существующую обработку банковских статусов backend не удалять. Банк всё равно способен выполнить возврат: такая ситуация требует ручной проверки до выплаты рефереру; автоматическая корректность баланса после возврата здесь не обещается.

**Не удаляем:** tenant/user isolation, серверную цену, immutable payment snapshot, первую оплату за всю историю существующего владельца биллинга, точность RUB/копеек, idempotency и защиту ручных выплат. Это предотвращение неправильных списаний/начислений, а не новая инфраструктура.

## C1. Повторное использование tracking и одна новая проверка кода

Base gateway — существующий `/tracking`; пути Fastify ниже без этого префикса. Backend-only `X-Api-Key`, текущие organization/product validation и явно настроенный product/program реферальной программы; cookie/participant JWT не заменяет служебное право записи подтверждённой продажи.

| Операция | Статус и согласованный контракт |
| --- | --- |
| `POST /v1/referrals/resolve` | **NEW, без бизнес-записей.** `{productId,programId,customerExternalId,code}` → новый ReferralCodeResolution: codeId/canonicalCode/productId/programId/referrerParticipantId/safe alias, независимые buyerDiscount/commission policy, calculationVersion и frozen rule IDs/config. Native normalizeCode/isRefcodeFormat, проверки dates/currency/ownership. Служебный API-key limiter может писать счётчик; participant/referral/event/reward не создаются. Полный D1 ReferralSnapshotV1 с нашим тарифом/acceptedAt собирает backend, RefRef тарифами не управляет. |
| `POST /v1/track/signup` | **EXISTS.** Принимает refcode и создаёт participant/referral/signup. Не использовать как проверку промокода и не вызывать перед оплатой ради привязки: у него есть записи и signup rewards. Общую существующую логику поиска/связи переиспользовать внутри purchase transaction. |
| `POST /v1/track/purchase` | **EXISTS, расширить**, не создавать `/referrals/conversions`. `{timestamp,productId,programId,payload:{userId,orderId,orderAmountMinor,currency:"RUB",customer:{name,email},referralSnapshot:ReferralSnapshotV1}}`. Customer берётся backend из профиля пользователя, оформившего оплату. Цены уже внутри snapshot, второй pricing не дублировать; actual paid amount сверить с payable. Одна transaction: participant/данные покупателя/referral/code-use→purchase→ожидаемые rewards. Ответ: native success/message/eventId + productId/programId/orderId/participantId/referralId/rewardIds/duplicate; route schemas/OpenAPI/HTTP callers согласованы. |

`payload.userId` = существующий billing owner нашего сервера (сейчас tenantId из проверенного контекста), не actorUserId/workspaceId. `payload.orderId` = неизменный backend checkout.id; merchant orderId/session/payment ID банка остаются отдельными. Product — стабильный scope, не ID API key. `timestamp` — сохранённое время подтверждения/банковского события с явным происхождением, не новый now на каждом повторе.

**Участник не равен платившему клиенту:** participant — native запись участника продукта, не доказательство покупки и не учётная запись для входа. В существующих signup/widget путях он создаётся без оплаты; также может уже существовать при повторе обработки той же покупки. Поиск/upsert — по unique(productId,externalId), не по имени/email. Для нашего сценария externalId = существующий billing owner backend. Это переиспользование текущей модели и защита от повторов, не задел на скидки повторным покупкам.

**Право на первую покупку:** backend проверяет всю доказанную историю успешных оплат billing owner, включая оплаты без кода; наличие participant не означает paid, отсутствие не означает never-paid. Уже плативший owner не получает новую скидку/комиссию независимо от RefRef profile, пользователя, workspace или нового order. Существующий participant без прошлой оплаты может участвовать в первой покупке; неизвестная история не считается пустой. Повтор того же подтверждённого order возвращает прежний результат, не новое право.

**Данные покупателя:** backend автоматически берёт имя и email пользователя, оформившего оплату, и передаёт `customer: {name, email}`. RefRef сохраняет их в существующих participant.name/email. Используется обычная учётная запись покупателя, без отдельной карточки или выбора другого ответственного за оплату. Эти данные не добавляются в ReferralSnapshotV1 и не используются как ключи покупки/начисления. Legacy запрос без customer не стирает профиль.

**Какие данные получает RefRef:** проверенные служебным ключом organization/product/program, внешний ID платящего billing owner, ID нашей оплаты, подтверждённую сумму/валюту/время, принятые условия кода **и имя/email покупателя из его профиля**. Банковские секреты, сведения карты, полный ответ банка и доступ к нашей БД не передаются. Merchant orderId, bank payment/session IDs и доказательство проверки остаются у backend; покупка связана по checkout.id и product scope. Имя/email сохраняются в participant, не в общем metadata; signup ради их заполнения не вызывается.

**Деньги:** buyerDiscount — none/fixed/percent; commission отдельно. В новом контракте подтверждённой покупки orderAmountMinor — итог к оплате в копейках, currency обязательна; base − discount = orderAmountMinor > 0, safe nonnegative integers. Старый orderAmount — действующий major-unit контракт остальных tracking consumers, не молча переименованная сумма: прежние сценарии других программ сохраняются, все callers нашей программы переходят на явную minor-unit форму без неоднозначных двух сумм. G1/G2 задают округление и базу комиссии. Minimum buyer discount не отменяет valid code/commission.

**Фиксация:** сервер повторно проверяет только успешно applied code, сохраняет исходные codeId/referrer/rules/pricing до банковского POST. Последующий purchase доверяет этому авторизованному snapshot в пределах разрешённого scope, а не заново считает по изменённой программе. Без applied referral обычная покупка не вызывает RefRef. Failed applied recheck не повышает показанную цену молча: ошибка, base display, следующая явная покупка без кода.

**Защита от повторов — разные уровни:** ниже native ограничения схемы/миграций; безопасный возврат прежнего результата и общая transaction дорабатываются в R2, это не утверждение полной готовности текущего purchase.

| Что защищается | Ключ / правило |
| --- | --- |
| Участник | Уже unique(productId,externalId); externalId — наш billing owner, не email/actor. |
| Одна покупка | Уже event unique(productId,eventDefinitionId,businessKey), где definition=purchase, businessKey=backend checkout.id из orderId. Смена program/owner/amount/currency/terms для того же order — 409, не новая продажа. |
| Одно начисление | Уже reward unique(eventId,rewardRuleId,participantId); повтор обработки не создаёт второе начисление тому же получателю по тому же правилу. |
| Первая покупка за историю | Новые B1 lifetime признаки backend и R2 firstPurchaseEventId на native participant: другой order/key не обходит прошлую успешную оплату. |

Нет signup→purchase двухшагового протокола, новой conversion/receipt таблицы, refund API или фоновых retries. Имя/email не участвуют в этих ключах.

**Ошибки/форматы:** C0; 400 invalid body, 401/403 auth/scope, 404 code, 422 inactive/conditions, 409 conflict, 503 unavailable. HTTP ответы сохраняют безопасный machine-readable code/status; не возвращают raw bank/transport payload. Timeout не доказывает отсутствие записи; явный повтор того же order безопасен.

**Хранение и подтверждение — D1/D2 backend:** ReferralCodeResolution/ReferralSnapshotV1 и PurchaseEventMetadataV2 описаны C1/OpenAPI; переиспользовать подходящие контрактные типы/схемы SDK, иначе валидировать локально штатными средствами. Общих ORM/бизнес-сервисов/БД нет, conversions таблица не нужна. CurrencyType — native USD/EUR/GBP/RUB, firstPaidOnly — условие программы; backend нашего продукта требует RUB/true. В `event.metadata JSONB` V2 — orderId, actual orderAmountMinor/currency и полный snapshot, без второй pricing. Native columns сохраняют product/program/participant/referral/businessKey; новый occurredAt TIMESTAMPTZ — исходный timestamp, event.id — TEXT. V1 major события не переписывать в minor; native config правил также сохраняет свои unit/amount.

**Снимок и подтверждение:** полный принятый ReferralSnapshotV1, включая calculationVersion, переносится backend→purchase→event.metadata без пересборки по live program/rules. Неизвестные версии отклоняются, версия участвует в согласованном hash/fingerprint; набор правил G1 не меняется за прежним номером. Native scalar links — согласованная проекция с проверками scope/суммы, не второй источник редактируемых условий. Backend хранит проверенный eventId и вычисляет служебное подтверждение по D2, не добавляет отдельный статус/копию rewards и не показывает покупателю сбой чужой комиссии.

**Event ≠ награда ≠ выплата:** текущий engine может поставить processed без rewards (нет program/rules). Новая интегрированная transaction должна проверить применённые frozen rules и созданные результаты, а не вернуть только eventId. Подтверждение API не означает approved/disbursed/completed payout. Replay возвращает прежние event/reward IDs; отсутствие ожидаемого результата — явная ошибка, не ложное начисление.

- [ ] Запрос/резерв/начало/подтверждение исполнять под стабильным lock participant/currency и условными переходами. requested→processing закрепляет одного оператора; processing не истекает сам. completed неизменяем; повтор возвращает тот же результат, другая сумма/reference конфликтует. При неизвестном исходе перевода ни повторного перевода, ни освобождения резерва.
- [ ] Отделить бизнес-переходы выплаты от получения подтверждения. Общая внутренняя операция completePayout проверяет сумму/валюту/внешнюю операцию и завершает резерв. Сейчас её вызывает только авторизованный admin после ручного перевода; будущий проверенный callback провайдера сможет вызвать ту же логику без смены модели/нейминга. Клиентский executionMethod/source не является подтверждением и не даёт права отмечать completed.
- [ ] Перед ручным переводом оператор сверяет фактическую оплату и отсутствие возврата в backend/банке; спорный случай — без выплаты до разбора. Refund/reversal/debt автоматизация исключена. Сверка использует существующий операторский доступ, scoped detail/trace reads B2/B3 и native event/referral/reward RefRef. Новых отчётных API или подключения RefRef к БД/банковским секретам backend нет.

**Новые/расширяемые tRPC контракты:** participantPortal.summary/history/requestPayout{amountMinor,currency,idempotencyKey} — только проверенный владелец, отдельные остатки по каждой валюте. payouts.list/claim/confirmPaid/reject — явный authorized product и org admin; confirmPaid{payoutId,externalReference,amountMinor,currency,completedAt,idempotencyKey} использует доверенного manual actor. Новый финансовый путь не выбирает первый product; approval/status mutations получают enum переходов/admin checks. Валюту/сумму проверяет сервер, выбор клиента не подтверждает перевод.

**Миграции:** payout и необходимые scope/owner/FK/индексы существующих записей; owner FK нужен только для выбранного в G3 RefRef-account linkage, существующий product JWT не выдумывается заново. **Готово, когда:** own portal не видит чужие данные, approved/pending/legacy суммы сходятся, частичный вывод не погашает всю награду, две заявки/два оператора/повтор confirmation не дают лишний перевод, модель завершения не привязана к ручному банку.

## G. Бизнес-параметры текущего объёма

**G1:** реальные discount/commission значения, точность и одно согласованное правило расчёта/округления текущей calculationVersion, условия/validity; нулевой payable не выдавать за успешную банковскую оплату. Варианты округления и их выбор в интерфейсе сейчас не проектировать; до утверждения правила и конкретных пограничных примеров программу не активировать.

**G2 — согласовано пользователем 2026-10-24:** процент комиссии нашей программы берётся только от фактически уплаченной подтверждённой суммы после скидки (`payable_amount`). При отсутствии скидки это полная оплаченная цена. Новые base_amount percentage-условия backend отклоняет до принятия/банка; fixed commission не переосмысливается. Общий RefRef сохраняет возможность иных программ и неизменные ранее принятые snapshot/basis. Reversal/debt policy не проектируется.

**G3:** RefRef-person → native referrer participant и отдельно проверенный получатель выплаты; регистрация реферера в backend AI-маркетолога не требуется. Не придумывать ownership evidence/rates/периоды/минимум выплат. Прежние ownership/self-referral/recipient и отдельный Approve Reward сохраняются. Историческая полнота оплат и подтверждение ВТБ — технические проверки B1 в существующем backend.
